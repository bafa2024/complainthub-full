Project Specification: Brand Complaint Management System
Project Overview & Scope
This project aims to develop a Brand Complaint Management System that allows businesses to manage customer complaints, feedback, and suggestions across multiple channels with the help of AI-driven bots. The system will consist of a conversational BOT API (voicebot/chatbot) built in Python and a set of web portals (Brand, User, Admin) built using Bubble’s no-code platform. All components must be delivered within a 1-month timeline, fully deployed on the client’s hosting environment. The scope includes building all listed features, integrating required third-party services, designing the UI/UX, and ensuring the system is secure and scalable. We outline below the technical scope, key features, platform specifications, and criteria for evaluating and selecting the development team.
Timeline & Deliverables
The expected project duration is 4 weeks (1 month) from kickoff to deployment. Key milestones and deliverables include:
•	Week 1: Finalize requirements and design – The freelancer will review all features with the client, propose an application architecture, and create UI/UX mockups for the Bubble interfaces. Deliverable: Design prototypes and technical design documentation.
•	Week 2: Implement BOT API and core backend features – Set up the Python backend for voice/chatbot functionality, integrate AI (OpenAI/ChatGPT) and third-party APIs (Deepgram, Google Cloud, telephony APIs). Begin configuring the Bubble environment for portals. Deliverable: Initial BOT API endpoints and a basic Bubble app structure.
•	Week 3: Develop web portals (Brand, User, Admin) – Complete building the Bubble frontends, including pages for dashboards, ticket views, and forms. Connect the Bubble app with the Python backend via API workflows for ticket creation and updates. Deliverable: Functional Brand, User, and Admin portal with integration to the backend.
•	Week 4: Testing, refinements, and deployment – Conduct thorough testing (unit testing for Python code, integration testing for end-to-end flows, and user acceptance testing with sample brands/users). Refine the UI/UX and fix any bugs. Prepare documentation (technical docs, user guides) and deploy the solution on the client’s environment (e.g. client’s cloud server for the Python API and transferring the Bubble app to the client’s Bubble account/domain). Deliverable: Complete system delivery including source code, deployed applications, and documentation.
All deliverables will be hosted on the client’s environment – meaning the Python backend will run on servers or cloud instances provided by the client, and the Bubble application will be set up under the client’s account or a domain they control. The freelancer is expected to assist in deployment and knowledge transfer by the end of Week 4.




Platform & Technology Stack
•	No-Code Frontend/Dashboard: The Brand portal, User portal, and Admin panel will be built using Bubble (a no-code web app builder). Using Bubble allows rapid development of custom dashboards with integration capabilitiesbubble.io. Bubble will handle the UI, workflows, and database for ticket information, while connecting to external APIs for advanced functionality. The freelancer should utilize Bubble’s visual design tools and plugins (e.g. API Connector) to integrate with the Python backend and third-party services.
•	Backend and BOT Engine: The conversational bot and supporting APIs will be implemented in Python. Python is preferred for its robust libraries and AI integration support. The developer may use frameworks like FastAPI or Flask to build RESTful APIs for the bot and other backend services. The core BOT logic will utilize OpenAI’s ChatGPT (via API) to converse with users and collect complaint details. This will enable natural language understanding and response generation so that users can talk to the bot as they would to a human agent. (For example, Twilio’s ConversationRelay can stream voice to an AI model in real-time, allowing creation of high-performance voice bots integrated with OpenAI twilio.com.)
•	AI and Voice Processing Services: For voice calls and voice messages, the system will use Speech-to-Text (STT) and Text-to-Speech (TTS) services. Specifically, Deepgram’s API and Google Cloud’s Speech services will be integrated. Deepgram offers real-time transcription with additional intelligence like sentiment analysisdevelopers.deepgram.com, which will help determine caller sentiment and urgency. Google Cloud’s Natural Language API will be used for advanced text analysis – to gauge sentiment polarity and intensitycloud.google.com, to classify the content of complaints into categories, and to perform content moderation (e.g. detect toxic or abusive language in the complaint)cloud.google.com. Combining these, the system can classify each interaction by urgency level, abuse/profanity level, and type (complaint, feedback, suggestion, or support inquiry).
•	Telephony and Messaging Integration: The bot will interact with users across multiple channels. For voice calls (telephone support), integration with cloud telephony providers like Twilio, Knowlarity, Exotel, Ozonetel, or MyOperator is required. These platforms provide Voice APIs and call routing capabilities to connect the phone network to our bot backendexotel.com. For messaging channels, the system will connect to APIs for WhatsApp, Telegram, Facebook Messenger, Instagram Direct, LinkedIn, and a web chat widget. Wherever possible, existing integrations or gateways (such as Twilio’s WhatsApp API or Facebook Messenger API) will be utilized. Each channel will route user messages or calls to the Python BOT API, which processes the input (with AI/NLP) and returns responses (text or TTS audio).
•	Data Storage: Bubble will maintain the primary database for ticket records, user profiles, brand accounts, etc., as part of the no-code app. The Python backend may use a lightweight database or in-memory store if needed (for example, to store conversational context or user session data for returning users), but persistent data about tickets and users should reside in the Bubble app’s database for easy access via the Brand/User portals. Any conversational logs needed for self-training can be stored either in Bubble (as part of ticket logs) or a separate database as appropriate.
•	Hosting Environment: All components will be deployed in the client’s environment. The Bubble application will be transferred to the client (who will assume ownership of the app and its data on Bubble’s cloud). The Python backend will be containerized or set up on a server under the client’s control (e.g. a Docker container on AWS, Azure, etc., or a server machine provided by the client). The freelancer must ensure that any required API keys or credentials for third-party services (OpenAI, Deepgram, Twilio, etc.) can be configured in a secure way in the client’s environment (e.g. stored in Bubble settings or environment variables on the server). All deliverables should run on the client’s infrastructure with no dependency on the developer’s environment.
Functional Requirements & Features
The system consists of several integrated components. Below we detail the features of each major module (A: Bot API, B: Brand Portal, C: User Portal, D: Admin Panel) and additional workflows:
A. BOT API (Python Backend)
The BOT API is the AI-driven engine that interacts with end-users via voice and chat, collects their input, and creates complaint tickets. The freelancer will implement the following features in the Python backend:
•	Conversational Voicebot & Chatbot: Develop APIs for both voice calls and text chats that interface with ChatGPT (OpenAI). The bot should greet the user, understand their issue (via voice or text), ask relevant questions to gather details, and confirm the information to create a complaint ticket. Using OpenAI’s large language model ensures the bot can engage in natural dialogue and ask clarifying questions. The voicebot will use telephony integration to handle phone calls: for example, Twilio’s programmable voice can stream call audio to our bot, and the bot’s replies are converted to speech and played back to the caller in real-timetwilio.com. For text channels (WhatsApp, web chat, etc.), the chatbot API will handle incoming text messages similarly. The bot should log each conversation and upon completion, trigger creation of a ticket in the system (via an API call to the Bubble app or direct DB write).
•	Sentiment Analysis & Classification: Implement logic to analyze the user’s input (both text and voice) to determine urgency, abusive language, and category of the issue. This involves using Deepgram’s sentiment analysis on transcribed calls and Google Cloud’s Natural Language processing. For instance, Deepgram can provide a sentiment score for the entire call or segments of itdevelopers.deepgram.com, and Google’s NL API can categorize text into predefined categories and detect toxicity or insultscloud.google.com. The bot will use these signals to mark the ticket with:
•	Urgency level: e.g. high, medium, low – based on the user’s tone and words (e.g. very negative sentiment or urgent language might mark it high priority).
•	Abuse level: flag if the user is using abusive or profane language, or if the content is toxic/derogatory. This could trigger special handling (for example, if abuse level is high, maybe shorter dialogues or alerts to admins).
•	Category: Determine if the user’s input is a Complaint, Feedback, Suggestion, or Support query. Keywords or intent recognition can be used (e.g. “complain about bad service” vs “suggest improvement” vs general query). We may leverage AI classification or simple keyword rules for this. Google’s content classification model can help assign categories if trained appropriately.


•	Self-Learning Capability: Design the bot to improve over time with each brand-specific conversation. This means the bot should be able to learn from past interactions for a particular brand. In practice, this could involve fine-tuning prompts or maintaining an FAQ knowledge base per brand. For example, if users of Brand X frequently ask about a certain issue, the bot could learn to provide a more specific response or gather certain info automatically next time. The freelancer should propose a method for this “self-training” – it could be as simple as storing resolved Q&A pairs and programming the bot to recall them for future similar queries, or using OpenAI fine-tuning on conversation logs after enough data is gathered.
•	User Privacy & Data Isolation: Each complaint conversation and ticket must be isolated to the specific user and brand. The system should not leak data between brands – Brand A should never see Brand B’s complaints, and the bot should not use another brand’s data in conversation. If the AI uses any context beyond the single conversation, it should be restricted to that brand’s domain (e.g. referencing only Brand-specific information). Additionally, when notifying brands (e.g. via email or portal), the user’s personal details should be masked or only shared as needed (for example, use a unique ticket ID instead of full user name in initial emails). This ensures compliance with privacy standards and builds user trust.
•	Persistent User Recognition: Implement a way to recognize returning users and remember their past issues. For voice calls, this could be done by the caller’s phone number – if the same number calls again, the bot can retrieve past tickets associated with it and greet the user with context (e.g. “Welcome back, we see you had an issue with your laptop last month – are you calling about a new issue or a follow-up?”). For chat channels, a user’s account or phone number (for WhatsApp/Telegram) can serve as an identifier. The bot should maintain a lightweight profile or at least fetch the last unresolved ticket for that user. This persistent recognition aims to avoid making the user repeat information and provide a more personalized experience.
•	Multilingual Support: The bot will support multiple languages to accommodate users in different regions. At minimum, it will handle English and one regional language per deployment (to be specified by the client – for example, a Hindi option for India, etc.). The bot should detect or allow the user to choose the language at the start. Using language detection APIs or user input (e.g. “press 1 for English, 2 for Hindi” on a call, or auto-detecting language from text) to route to the appropriate language model. OpenAI’s models can work in many languages, and Google’s translation or language-specific models can assist if needed. The interface (voice prompts or chat UI) should be localized accordingly. All system messages and knowledge base content should be translatable. Note: The initial development can focus on English (as the default) and ensure the framework is in place for adding other languages easily.
•	Omnichannel Integration: The bot should function across multiple channels:
•	Phone (Voice calls): via Cloud Telephony (integrate with Twilio, Knowlarity, Exotel, etc. as needed). When a user calls a provided number, the call is forwarded to the bot’s voice endpoint. Twilio for example can use a WebSocket to stream the call audio to our Python service and stream back the AI’s spoken responsestwilio.com.
•	WhatsApp: using WhatsApp Business API (possibly through Twilio’s WhatsApp sandbox or direct WhatsApp API) to handle text messages.

•	Telegram: via Telegram bot API integration.
•	Facebook Messenger, Instagram DMs, LinkedIn messages: using each platform’s chatbot integration (this might involve setting up apps on those platforms and subscribing to messages events which are then forwarded to our bot API).
•	Web Chat Widget: a chat widget that can be embedded on the client’s website, which will send user messages to the chatbot API and display responses.
The freelancer should implement or configure connectors for each required channel. The goal is that a user can lodge a complaint through any of these channels and receive a consistent BOT experience. All these inputs ultimately create the same kind of ticket in the system.
•	Integration with Telephony Providers: As part of the above, integrate specifically with APIs of Twilio, Knowlarity, Exotel, Ozonetel, and MyOperator as needed for call handling and SMS/WhatsApp. The system might allow using one provider or multiple based on client preference or regional availability. For example, Twilio provides global numbers and a powerful Voice API, whereas Knowlarity/Exotel are popular in India for cloud telephony. The BOT should be abstracted enough to support multiple providers. For instance, use Twilio’s API for buying a phone number and receiving calls for one deployment, or use Exotel’s API for another – the brand portal should allow configuration (we will discuss the Brand Portal feature for number purchase below). These integrations should cover making outbound calls as well (for follow-ups), sending WhatsApp or SMS notifications, etc. The developer should be familiar with such telephony API usage (or be ready to learn quickly) – many have Python SDKs available.
•	Speech-to-Text Transcription: All voice calls or voice messages should be transcribed to text in order for the AI to understand them. Implement the pipeline to send audio to Deepgram’s API or Google’s Speech API. Deepgram is preferred for its accuracy and built-in intelligence (as noted, it can return sentiment data along with the transcript). Google Cloud Speech-to-Text could be used as a fallback or for languages Deepgram doesn’t support. The transcription results will feed into the ChatGPT prompt for generating a reply, and also be saved with the ticket (so that brand agents can read what the user said, and for audit purposes).
•	Limited Dialog Turns: To maintain focus and efficiency, the bot should limit the number of back-and-forth questions in one session to 3–5 questions (after the initial user complaint description). This means the bot will try to gather the necessary details within a few prompts. The exact limit can be refined, but the idea is to avoid lengthy conversations – the bot should collect the core information needed to create a ticket (like user name, account or order number if applicable, brief description of issue, any specific detail needed), and then stop. If the issue is complex, the bot should create the ticket and inform the user that a human will follow up if more info is needed, rather than asking endless questions. This feature ensures a consistent and quick interaction, respecting the user’s time.
•	Unique Voice per User: For voice interactions, implement a feature such that each user hears a consistent voice from the bot across calls. This could be achieved by assigning different TTS voice profiles to different users (or at least different phone numbers). For example, User A’s calls always use a female voice and User B always hears a male voice (or different accents, etc.), making the experience feel more personalized. There are many TTS voices available (via providers like Google, Amazon Polly, etc.), so the system can randomly assign one voice to a new user and then recall that for future interactions. This is a nice-to-have feature that can make the interaction more engaging. It also prevents a scenario where a returning user is confused by the bot sounding completely different on different days. The developer should incorporate this by storing the “voice ID” per user and configuring the TTS engine accordingly for each response.
Overall, the BOT API should be designed for high availability and quick response. Latency should be minimized (for voice calls especially, aim for near real-time response to avoid dead air). Twilio’s streaming API and Deepgram’s low-latency transcription are useful here. The conversations should be logged securely, and errors should be handled gracefully (if the AI fails or an API is down, the bot should have fallback responses or ask the user to hold while connecting to a human if possible).
B. Brand Portal (Bubble Application)
The Brand Portal is a web application (built with Bubble) where brand clients (companies using this system) will log in to view and manage the complaints and feedback submitted by their customers. The portal will have the following features:
•	Secure Brand Login: Each brand gets its own login (with one or multiple user accounts possible per brand – e.g. a company might have a team of support agents, each with their own credentials to the portal). Upon login, the brand user will only see data relevant to their brand. We will implement role-based access if needed (e.g. an admin user for the brand who can manage their team, vs normal support agents who can just handle tickets). All data partitioning must ensure one brand cannot view another’s information.
•	Dashboard & Analytics: The landing page for a brand user will be a dashboard showing an overview of their complaint tickets and performance metrics. This includes stats like: number of new complaints, feedback, suggestions, support requests; status distribution (open, in-progress, resolved); average resolution time; user satisfaction scores; and perhaps charts or trends over time. Bubble’s capabilities for creating charts or using plugins for analytics can be leveraged here. The dashboard gives the brand a quick insight into how they are performing in customer service. The freelancer will design a clean dashboard UI (in line with UI/UX guidelines) that highlights the most important information upon login.
•	Ticket Management: The brand can view the list of tickets (complaints/feedback) lodged by users for their brand. They should be able to filter by category (complaint, feedback, etc.), status, date, or urgency. Clicking on a ticket opens the ticket detail page which contains the full history: user’s initial complaint (text and/or a playable voice recording if it was a voice complaint), any sentiment/abuse flags (as analyzed by the bot), and fields like timestamp, channel (e.g. via WhatsApp or phone), and user info (which might be limited to a nickname or ID to preserve anonymity until the brand engages). On this page, brand agents can update the ticket status (e.g. mark as in progress, resolved), assign it to a team member, and post responses or notes. If a brand agent replies via text on this portal, that response can be sent to the user (via email or via the original channel if feasible – e.g. sending a WhatsApp message via the system). The portal essentially functions as a lightweight CRM for handling tickets.
•	Toll-Free Number Generation (API-based): One key feature is to allow brands to quickly set up a toll-free phone number or virtual number for their customers to call. Through the portal, a brand user can request a phone number. The system will integrate with telephony provider APIs (like Twilio, Knowlarity, etc.) to purchase or allocate a number on the fly via API. For example, using Twilio’s API to buy a number in a given country, or using Knowlarity’s API to allocate a virtual number. This number will be linked to that brand and configured to route calls to our voicebot. The portal should show the assigned number to the brand once provisioned. (If API-based auto-provisioning is not feasible for all providers, an alternative is the admin could manually set up numbers and assign to brand, but the requirement here suggests automation.) This feature gives brands a dedicated line for the complaint system without manual setup. It should also handle failure cases (e.g. if no number is available, inform and have an admin follow up).
•	Credit Balance & Billing Management: The system will operate on a credit or billing mechanism for certain features. Each brand will have a credit balance visible in their account. This balance will be decremented according to usage rules (explained below, e.g. if a complaint remains unresolved beyond 24 hours, a fee is charged). The portal should show the current balance, usage history, and allow the brand to top-up their credits. Top-up could be implemented via integrating a payment gateway on Bubble (for example, Stripe or a local payment provider) or by informing them of an invoice. For simplicity, we might implement a “Add Credits” button that triggers a payment workflow. Once payment is confirmed, credits are added to their account. Alternatively, if online payment is out of scope, the portal can show a button to request more credits and the admin can fulfill it manually, but the preference per the spec is an automated top-up. The freelancer should clarify the payment method with the client and integrate accordingly.
•	Ticket Assignment: Within the brand portal, provide the ability to assign tickets to specific team members (if the brand has multiple users). For example, a supervisor can assign a particular complaint to a certain support agent for resolution. This can be as simple as a dropdown on the ticket detail to set “Assignee” (with a list of that brand’s user accounts). The assigned person could get a notification (email or within portal) that a ticket is assigned to them. This feature helps brands organize their workflow internally.
•	Auto-Routing of Tickets: In addition to manual assignment, the system should have auto-routing rules based on category or other criteria. For instance, all “support” tickets (which might be simple queries) could automatically be assigned to a Level-1 support queue, whereas “complaints” might be tagged for a special team. Categories like feedback/suggestions might not need assignment and just be collected for review. We can implement a simple rule engine: e.g., if category = “Feedback” or “Suggestion”, mark the ticket as “unassigned” but accessible to all, or assign to a default user; if category = “Complaint”, and the brand has a specific “complaint manager” user, auto-assign to them, etc. The specifics can be configured in brand settings or just coded in for now. This automation ensures critical issues don’t sit unattended.
•	Differentiated Access (Free vs Paid features): The platform’s business model as described:
•	Feedback, Suggestions, Support tickets: free for the brand to access and respond to. This means brands can view and answer these types of submissions without incurring charges, encouraging them to use the platform for general engagement.
•	Complaints: have a potential cost if not resolved quickly. The portal should communicate this clearly. Possibly, complaints could be visible to the brand with a tag indicating they are in a “free resolution window (24h)” initially.
•	If a complaint is resolved within 24 hours by the brand, they are not charged (it remains free). The system should track the time since ticket creation and whether it’s resolved in time.
•	If the complaint remains unresolved after 24 hours, it triggers a charge of Rs. 50 (could deduct 50 credits from their balance). In exchange for this charge, the complaint remains open and possibly gets additional “visibility” (perhaps meaning it might be listed publicly until resolved, or escalated visibility to the user and admins).
•	After the 24h mark and charge, the brand can continue to work on the resolution. It’s implied that extended visibility could mean the complaint might show up on the public User Portal listing (to pressure resolution). The portal should highlight which complaints are beyond the free window and incurred charges.
The freelancer should implement logic to support this: a scheduled workflow (in Bubble or backend) can check tickets at 24h mark and then deduct credits & flag the ticket. The UI should show a countdown or a note like “Resolve within X hours to avoid charge”. Also, if a brand’s balance is low, warn them that unresolved complaints could not be extended (this ties into credit management).
•	User Satisfaction Rating (0–5): When a brand resolves a complaint, the user will be prompted (via follow-up bot call or on the user portal) to give a satisfaction rating. The brand portal should display these ratings for each ticket (once available) and an average score. For example, each resolved ticket might show a star rating 0-5 given by the user. The dashboard can have an average rating across all tickets. This encourages brands to keep consumers happy. The system should only show the rating to the brand after the user provides it (and if the user doesn’t provide one, it can show “N/A” or no rating).
•	CRM Integration via API/Webhooks: Many brands use existing CRM or support software (Zoho Desk, Salesforce Service Cloud, Freshdesk/Freshworks, Kapture CRM, LeadSquared, etc.). The portal will offer integration points to these systems. That means when a new complaint ticket is created, the system can automatically push it into the brand’s CRM (via API or webhook), and possibly vice versa (if the brand updates status in their CRM, our system could get a webhook to update the portal ticket). To implement this, we’ll likely have a settings page where the brand can enter their CRM API credentials or endpoint if they choose to integrate. For example, Zoho and Salesforce have APIs for creating cases; Freshworks and others have webhooks. We can support integration either by direct API calls (Bubble’s API connector can do this when a ticket is created) or by providing a webhook that the CRM can call. At minimum, we’ll document that we can integrate with these systems and possibly implement one or two as proof of concept if required. This feature is important for brands who don’t want to adopt a new dashboard but rather incorporate the complaints into their existing workflows. (Many telephony platforms and contact centers emphasize CRM integration – e.g., Exotel’s platform highlights CRM & system automationsexotel.com, which aligns with our approach here.)
The Brand Portal will be designed with ease of use in mind. It should mirror some design cues from modern support dashboards. The UI should be intuitive so that support agents can quickly adopt it. Also, real-time aspects: consider using Bubble’s capabilities for real-time updates (or periodic refresh) so that as new tickets come in (from the bot), they appear on the brand’s dashboard without the need for manual refresh. Notifications could be sent (maybe an email alert or browser notification) to brand users when a new complaint arrives, especially if urgent.
C. User Portal (Bubble Application)
The User Portal is a public-facing website and account portal for end-users (customers who lodge complaints). This serves two purposes: (1) to publicly list unresolved complaints which can be indexed by search engines (for SEO and accountability), and (2) to allow users to log in and track their own complaints.
 
Key features of the User Portal:
•	Public Listing of Unresolved Complaints: There will be a section (or separate page) on the site that shows a list of recent unresolved complaints for various brands. This is similar to consumer complaint forums where open issues are visible to all, creating pressure on brands to resolve them. Each complaint entry might show the brand name, date, a brief summary of the issue (possibly the title or first few lines of the complaint), and how long it’s been open. If the complaint was lodged via voice, the system will provide a playback option for the recorded voice clip – e.g. an audio player so visitors can hear the original complaint (after ensuring no sensitive personal info is mentioned in the recording). This transparency can improve SEO: user-generated complaint content can rank in search results when people search for that brand’s customer service issuesguaranteedremovals.com. (For example, platforms like PissedConsumer allow public airing of grievances to inform others and hold companies accountableguaranteedremovals.com.) We will ensure that any personal data (like user’s name or contact) is not exposed in these public listings – possibly by using an alias for the user and removing any such details from the visible text.
•	Inspired UI/UX from MouthShut/Trustpilot: The user experience should be akin to popular review and complaint sites. MouthShut and Trustpilot are mentioned inspirations – these platforms allow users to post reviews/complaints and companies to respond, and they feature structured listings and ratings. Our user portal should have a clean, modern interface where browsing complaints or reviews is easy. It may include features like search or filter by brand/category, upvote or comment (community interaction) on complaints, etc., if time permits. At minimum, the look-and-feel (colors, layout) should be professional and engaging, encouraging users to use the platform. We can include elements like overall rating of a brand (if we gather enough feedback data) or a way for users to share the complaint on social media (amplifying its visibility – which also pressures the brand).
•	User Registration & Dashboard: Users (consumers) can create an account or log in to view their submitted tickets. A user can sign up with email/phone or possibly through an OAuth if we integrate (not mandatory). The User Dashboard will show all complaints or feedback they have submitted, with statuses. For each ticket, the user can see if the brand has responded or marked it resolved, and what the current status is. They should also see the unique ticket ID and possibly the date/time and channel through which they submitted it. If the brand has responded or needs more info, the user can see those messages here (or via their email/WhatsApp, but the portal provides a central view).
•	Responding and Closing Tickets (User side): Users should be able to add additional information to their complaint if needed. For example, if a brand asks for more details, the user can log in and type a response or append a voice message to the ticket. The ability to append voice complaints to existing tickets means a user can record a follow-up voice note through the portal (assuming the device has a microphone) and attach it, which then becomes part of the ticket for the brand to review (transcription can be done on it as well). This is useful if, say, the user wasn’t clear initially or something changed. The user portal could provide a “Add voice update” button on an open ticket.
•	Reopening Tickets: If a ticket was marked resolved but the user is not satisfied, the portal should allow the user to reopen it within some window (as specified, maybe within 48 hours before it auto-closes fully). Reopening would notify the brand that the issue persists.
•	User Feedback and Rating: The portal will also be the place where users can rate their experience. When a ticket is resolved (or marked resolved), the user can log in and give a satisfaction rating (0 to 5 stars) and possibly a short comment. This rating, as mentioned, is fed back to the brand’s view. We should make this step accessible – possibly also send the user a direct link (via email/WhatsApp) to rate without logging in, but having it on the portal is a backup. We want to maximize the chance the user gives a rating.
•	Account Privacy: Users may be concerned about their identity being revealed publicly when they post complaints. The platform should perhaps give them an option to post anonymously or use just a first name / alias publicly. For example, the public listing might say “User1234” or “Anonymous” rather than the full name. But in the backend, we still know who they are and how to contact them. We will implement such privacy features in compliance with any relevant regulations.
Additionally, the user portal should be optimized for SEO (server-side rendering if possible, clean URLs for each complaint page, meta tags, etc. – Bubble has SEO settings that we can configure). Each unresolved complaint might have its own page that can be indexed (with the complaint title and brand in the URL). This will help search engines find them, similar to how Trustpilot pages often rank for “[Brand] reviews”business.trustpilot.com. The content being user-generated and frequently updated will naturally boost SEO.
D. Admin Panel (Bubble Application)
The Admin Panel is for the platform administrators (likely the client and their team) to oversee the entire system. This will also be built in Bubble (it could even be part of the same Bubble app as the Brand/User portals, with role-based access distinguishing admin users). Key features include:
•	Admin Dashboard & Reports: A comprehensive dashboard showing system-wide metrics: total number of brands onboarded, total complaints received (and breakdown by category), resolution rates, average user satisfaction across the platform, revenue earned (from the Rs.50 charges or any other billing), etc. Reports could include charts like number of new complaints per day, or performance of brands (maybe identifying top performing brands vs those with many unresolved issues). This helps the platform owner monitor usage and demonstrate value.
•	Manage Brands: Admins can create and edit Brand accounts. This includes registering a new brand (company) into the system, setting up their profile (name, industry, logo perhaps for display, contact info, default support email for notifications, etc.). The admin can also manage the brand’s credit balance here (e.g. add credits if a payment was received offline, or adjust credits as a goodwill). If a brand violates rules, admin could deactivate or delete their account from here. Essentially a CRUD interface for brand data.
•	Manage Users: Admin should be able to manage end-users and possibly brand users. For end-users, this might be minimal – we generally don’t interfere with customers, but admin might need to remove inappropriate content or ban abusive users if needed. For brand users, the admin panel could manage their accounts (reset passwords, add new brand admins if a company needs help, etc.).
•	Global Settings: A section for managing system-wide settings and credentials. For example:
•	API Keys/Credentials: The admin can input or update the API keys for Twilio, Deepgram, Google Cloud, WhatsApp, SMTP for emails, etc. This centralizes configuration so that the Python backend and Bubble can retrieve them from a secure place (Bubble can store these as app secrets).
•	IP Binding/Security: The admin panel might allow setting IP whitelisting for accessing the admin module (for enhanced security, only certain office IPs can log into admin). Also could manage other security settings like password policies for brand users, content moderation thresholds, etc.
•	Pricing/Rules: Admin could set the fee amount (currently Rs.50) or the free resolution window (24h) in case the model changes. Having these as configurable values in admin settings is useful.
•	Monitor Conversations/Tickets: A view for admins to see all tickets across all brands (primarily for moderation or support purposes). This includes listening to voice recordings if needed and reading transcripts. If there’s a dispute or an abusive situation, the admin can review the content. Admins should have the ability to remove any content that violates terms (e.g. extremely abusive language in a public comment might be hidden).
•	Manage Credits and Billing Logs: Admin can view a log of credit deductions and top-ups for each brand. This helps in reconciliation and billing support. For instance, see which complaints triggered the Rs.50 charge and ensure that matches the credits deducted.
•	Announcement/Broadcast (optional): The admin interface might include a way to send notifications or messages to all brand users (like a new feature announcement or maintenance notice). This is a nice-to-have if time permits.
•	Data Export: Admin should be able to export data (tickets, perhaps) in CSV for analysis or backup. Or even export brand-wise reports.
The Admin Panel essentially allows the client to run the platform independently after development. It should be user-friendly and secure. All critical actions (like deleting a brand or adjusting credits) might prompt confirmation to avoid mistakes. We’ll also implement admin-only privileges properly (so no brand user can accidentally access these pages).
Additional Functional Workflows
Beyond the core modules above, the system must handle some automated workflows for notifications and follow-ups:
•	Brand Notification on Complaint Creation: Whenever a new complaint is lodged by a user (via the bot), the system should automatically notify the respective brand outside of just the portal. Specifically, the requirement is to scrape or use the brand’s support email and send a notification email. This email will inform them: “You have a new complaint ticket [ID] from a customer.” It will include some details like the summary of the complaint and perhaps a link to the Brand Portal to view & respond. To maintain privacy, mask the user’s personal details in this email. For example, do not include the user’s full name or contact info – maybe just refer to the user as “a customer” or use a first name if appropriate. The idea is the brand is alerted immediately via email so they can respond even if they are not constantly logged into the portal. The “support email” for each brand could be determined in a couple ways: likely when onboarding a brand, the admin will input their support email address. “Scraping” might refer to automatically finding it from their website, but that may be unreliable; so we’ll use the provided contact if available. Integration with an email service (SMTP or a service like SendGrid) will be needed to send these emails from the system.
•	Follow-up and Resolution Confirmation: After a brand marks a complaint as resolved, the system initiates a follow-up process with the user to confirm and close the loop:
•	The BOT will call the user (for voice complaints) or message them (for chat complaints) after the resolution to ask if their issue is indeed resolved and if they are satisfied. For example, 24 hours after a ticket is marked resolved, an automated outbound call via the voice bot can be triggered. The bot might say: “Hello, we are calling to follow up on your complaint about [brief issue]. According to [Brand], your issue was resolved. If your issue is resolved satisfactorily, you can simply hang up or confirm. If not, you may indicate that you are not satisfied.” (The exact script will be designed).
•	If the user doesn’t answer the call, the system will then send a WhatsApp message and an email (if we have their email) with a similar follow-up text: asking them to reply if not resolved or to rate the service.
•	If 48 hours pass with no response from the user, the system will assume the complaint is resolved and will automatically mark the ticket as closed. At that point, the user’s opportunity to reopen might be closed (though we might still allow reopening but possibly treat it as a new complaint if too much time passed).
•	During that 48-hour window, if the user responds (e.g. says “Not resolved” via the bot call or clicks a link “Reopen” in the WhatsApp/email), the system should reopen the ticket and flag it for the brand that the user is unsatisfied, prompting further action.
•	After a ticket is confirmed resolved (either explicitly by user feedback or implicitly after 48 hours), the system finalizes it: no further follow-ups. The user is asked to provide the satisfaction rating (0-5) at this point if they haven’t already. We should capture that via the call (user can press a digit 0-5 in a phone call which we translate to rating) or via a web link.
•	Marking resolved with no reply should perhaps still allow the user to later log in and reopen within some grace period, but that detail can be adjusted.
This follow-up flow is important to ensure closure and measure success. The freelancer will implement automated scheduling for these follow-ups. For example, use Bubble’s backend workflows or scheduled API calls from the Python side to trigger the outbound communication. Twilio (or the chosen telephony API) will be used for the outbound call – using TTS to speak the follow-up message. For WhatsApp, an automated template message can be sent via the API. For email, a templated email goes out. All these messages should include the ticket reference and a way to respond (like a “reply with ‘REOPEN’ to reopen your case” or a link to the user portal).
In summary, these additional workflows ensure that once a complaint is created, the brand is immediately notified, and once it’s “resolved,” the user’s confirmation is obtained or the case is auto-closed after giving them a fair chance to respond.
